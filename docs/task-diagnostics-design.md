# 任务诊断与报告设计

## 目标

将 Veyr 从“原始 hook 事件查看器”升级为面向人的本地诊断工具。报告应先回答：

1. 本次任务发生了什么。
2. 哪些结论可信、哪些证据不完整。
3. 哪些事项值得处理，以及下一步如何验证。

原始事件仍保留为可下钻证据，但不再作为首屏主体。

## 数据分层

```text
原始 Hook 事件
  → 调用 / turn / task 投影
  → 规则发现与建议
  → HTML / JSON 报告
```

### 原始事件

保持宿主输入的时间、session、turn、tool use ID、工具名、有限结果摘要和来源。默认
不保存 prompt、命令参数、完整工具输出或 transcript 路径。

### 调用投影

以 `tool_use_id` 关联 `PreToolUse` 与 `PostToolUse`。

- 有可信 Pre 和 Post：生成一次 tool call，计算调用包络耗时。
- 只有 Pre：标记为未闭合调用。
- 只有 Post：标记为缺少开始证据，不伪造开始时间。
- `write_stdin` 结束原始 exec 时，仍按原 `tool_use_id` 归属，不计为新调用。
- 调用包络耗时使用 hook 的采集时间计算，必须标记为 `hook_envelope`；不冒充服务端
  或纯执行耗时。

### 任务投影

任务优先按明确 `turn_id` 聚合。缺少用户入口或最终交付边界时，报告为“观测 turn”而非
“端到端任务”。任务摘要包含：覆盖状态、调用数、可测包络耗时、已知等待、未闭合调用和
证据缺口。

## 结果与耗时语义

| 证据 | 可以显示 | 不可显示 |
| --- | --- | --- |
| Pre + Post 时间戳 | 调用包络耗时 | 服务端执行耗时 |
| `exit_code = 0` | 已知成功 | 业务结果正确 |
| 非零 `exit_code` / 结构化 error | 已知失败 | MCP/server 根因 |
| 只有 Post | 调用完成事件已观察到 | 成功、耗时、完整调用 |
| 无结构化结果 | 未知 | 成功或失败 |

## MCP 视图

当 `tool_name` 满足 `mcp__<server>__<tool>` 时，解析为 server 与工具名并聚合：调用数、
已知结果、未知结果、包络耗时分布和证据链接。

报告只能说“观察到的 MCP 调用”，不能据此声称列出了全部连接的 server 或全部可用工具。
非规范名称不推断 server 身份。

## Skill 证据视图

Skill 不是单一事件。报告按证据等级展示，禁止将读取文件当作成功执行：

| 证据等级 | 含义 |
| --- | --- |
| 明确请求 | app-server / 输入中明确请求 skill |
| 显式命令展开 | 观察到 `$skill` 或 host 支持的命令展开 |
| 文档读取 | 只观察到读取 `SKILL.md` |
| 关联活动 | 读取之后出现工具调用；仅时间相关 |
| 未观测 | 不是“未使用” |

当前 hook-only 路径不承诺完整 Skill 识别。后续 app-server 或已授权 transcript 输入可提升
证据等级，但报告必须保留来源和覆盖缺口。

## 报告结构

```text
任务摘要
├── 本次结论与覆盖状态
├── 值得关注的事项
├── 可执行建议
├── 工具调用时间线
├── MCP 调用
├── Skill 证据
├── 原始事件与证据链接
└── 覆盖边界
```

规则输出分为事实、候选解释与建议验证。样本不足时展示明细和下一步采集建议，不输出
“性能异常”。生命周期事件的未知状态不构成未知工具结果告警。

## 验证

- fixture：Pre/Post 配对、仅 Pre、仅 Post、非零退出、并行、乱序、MCP 名称、未知工具。
- 单元测试：调用关联、包络耗时、MCP 解析、Skill 证据分级、规则不误报生命周期事件。
- 真实 smoke test：真实 Codex Bash 调用应产生一个关联调用，并显示 `hook_envelope` 耗时。
- 报告验收：首屏不以原始事件表作为唯一主体；每个建议必须带对应证据或明确的缺失说明。
